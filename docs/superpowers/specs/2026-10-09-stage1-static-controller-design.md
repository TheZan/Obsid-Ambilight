# Этап 1 — Static Controller: дизайн

**Дата:** 2026-10-09
**Статус:** согласовано в обсуждении, ожидает просмотра спецификации
**Основа:** ТЗ «Obsid Ambilight» v1.0, разделы 3, 5, 7.5, 8, 9, 11–13; итоги Этапа 0 (`docs/protocol.md`)

## 1. Цель и границы

Лёгкое фоновое Windows-приложение, которое управляет статической подсветкой ленты
Yeelight Obsid (Chameleon2) по LAN: трей, окно настроек, автообнаружение,
сохранение настроек, статический цвет и яркость, переподключение, один экземпляр.

**Входит в Этап 1:**

- фоновый процесс с иконкой в трее, без окна при запуске;
- окно настроек по запросу (отдельный процесс);
- выбор и автоматическое обнаружение ленты, ручной IP, повторный поиск;
- режимы Off / Static, состояние Offline с переподключением;
- статический цвет, яркость 1–100 %, пресеты, применение без перезапуска;
- `config.toml` с проверкой значений;
- named mutex одного экземпляра;
- действие при выходе из приложения (п. 7.5 ТЗ);
- два языка интерфейса: русский и английский.

**Не входит (следующие этапы):** автозапуск через `HKCU\...\Run`, обработка
`WM_QUERYENDSESSION`/`WM_ENDSESSION`, сна и блокировки (Этап 3); Ambilight, захват
экрана, выбор монитора, калибровка LED (Этап 2); глобальная горячая клавиша.
Пункты меню и вкладки этих функций не показываются, пока функции не работают.

## 2. Ограничения из Этапа 0

- Сессия UDP открывается **по требованию** под команду и затем истекает сама.
  Фоновых keep-alive и опроса ленты нет: при сбоях Apple Home на Этапе 0 причина не
  установлена, поэтому LAN-трафик к ленте минимизирован (`docs/protocol.md`).
- Лента не отвечает на unicast M-SEARCH. Идентичность сохранённой ленты
  проверяется только multicast-поиском по `id`.
- Поиск идёт через каждый активный адаптер (VPN/TUN может держать маршрут
  по умолчанию) — уже реализовано в `discovery`.
- Внешние изменения из Apple Home приложение не отслеживает (допустимо в MVP, п. 4.4).

## 3. Архитектура: два процесса из одного exe

```text
obsid-ambilight.exe                      obsid-ambilight.exe --settings
┌─────────────────────────────────┐      ┌──────────────────────────────┐
│ UI-поток: скрытое окно + трей   │      │ eframe/egui (glow)           │
│ IPC-сервер (named pipe)         │◀────▶│ IPC-клиент, опрос ~4 Гц      │
│ Поток ленты (worker)            │ JSON │ живёт, пока открыто окно     │
│  └ Controller (чистая логика)   │      └──────────────────────────────┘
│  └ DeviceLink → protocol/…      │
│ Единственный писатель config    │
└─────────────────────────────────┘
```

- **Фоновый процесс** запускается без аргументов, держит трей, поток ленты,
  IPC-сервер и mutex. Цель по ресурсам в Static — до 35 МБ RAM, до 1 % CPU.
- **Процесс настроек** запускается фоновым процессом (`--settings`) по клику
  в трее и завершается при закрытии окна, освобождая GPU-контекст. С лентой
  напрямую не работает.
- Отклонены: окно egui в том же процессе (GPU-контекст живёт всё время,
  противоречит п. 8.2 ТЗ); окно в отдельном потоке (winit создаёт event loop один
  раз за процесс — окно нельзя открыть повторно).

## 4. Контроллер ленты

### 4.1. Поток и команды

Один поток (worker) владеет подключением к ленте. Все изменения состояния
устройства проходят через его очередь (`std::sync::mpsc`) — гонки исключены.

Команды: `ApplyStatic { color, brightness }`, `SetPower(bool)`,
`SelectDevice(DeviceRef)` (по id из найденных или ручной IP), `Discover`,
`TestConnection`, `UpdateSettings(..)`, `Exit`.

**Схлопывание:** перед выполнением worker вычитывает очередь целиком; из подряд
идущих `ApplyStatic`/`SetPower` остаётся последнее значение. Частота команд к ленте
при перетаскивании — не более ~5 в секунду, последнее значение отправляется всегда.

### 4.2. Состояния

```text
NoDevice ──выбор──▶ Connecting ──успех──▶ Ready(Off | Static)
                       │                      │ ошибка команды
                       ▼                      ▼
                    Offline ◀─────────────────┘
          повторы: 2 с → … → 5 мин, equal jitter, без лимита попыток
          после восстановления: применить последнее состояние пользователя (Static или Off)
```

- Ambilight после разрыва автоматически не включается (п. 5.4 ТЗ; на Этапе 1 его нет).
- Потеря связи обнаруживается только по неуспешной команде (опроса нет).

### 4.3. Разрешение ленты

1. Если задан `manual_ip` — подключаться только по нему (рукопожатие сессии).
2. Иначе multicast-поиск, совпадение по `id` → обновить `last_ip`.
3. Если не найдена и есть `last_ip` — попробовать рукопожатие на нём; успех
   помечается в состоянии как «не подтверждено по id».
4. Иначе — Offline с повторами.

### 4.4. Первый запуск и запуск приложения

- Нет сохранённой ленты: поиск; ровно одна Chameleon2 → выбрать автоматически и
  применить Static; ноль или несколько → NoDevice и открыть окно настроек на
  вкладке «Устройство».
- Есть сохранённая лента и `startup.power_on = true` → найти → включить →
  применить статический цвет (п. 7.1 ТЗ, шаги 1–7 без автозапуска).

### 4.5. Тестируемость

`Controller` — чистая машина состояний без потоков, сети и часов. Вход: событие
(команда, результат операции, наступление таймера) и текущее `Instant`. Выход:
список действий (`Resolve`, `ApplyStatic`, `PowerOff`, `Discover`, `SaveConfig`,
`ScheduleRetry(at)`, `PublishStatus`). Worker исполняет действия через трейт
`DeviceLink`, реализованный поверх `protocol`/`discovery`; в тестах — фейк.

## 5. Трей

- Скрытое **обычное** окно верхнего уровня (не `HWND_MESSAGE`): на Этапе 3 оно же
  получит широковещательные сообщения сеанса и питания. Обработка `TaskbarCreated`
  для восстановления иконки после перезапуска Проводника.
- Иконка рисуется программно под DPI: Static — круг текущего цвета; Off — серый
  контур; Connecting — жёлтая точка; Offline/NoDevice — красная точка.
- Подсказка: `Obsid Ambilight — Static #F5D4A1 · 40% · 192.168.1.85`.
- Меню (ЛКМ и ПКМ), строится заново при каждом открытии:
  строка состояния (неактивная); включить/выключить подсветку; «Цвет ▸» — пресеты
  с цветными квадратиками и «Другой цвет…» (открывает настройки, вкладка
  «Подсветка»); «Яркость ▸» 10–100 % с отметкой текущей; «Искать ленту снова»;
  «Настройки…»; «Выход». Двойной клик по иконке — настройки.
- Всплывающих уведомлений нет.

## 6. Локализация

- Языки: русский, английский. Без внешних зависимостей: структура `Strings` с
  полем на каждую строку и два экземпляра `RU`/`EN` — пропущенный перевод
  не компилируется. Параметризованные строки — функции.
- `app.language = "auto" | "ru" | "en"`; `auto` — по языку интерфейса Windows
  (`GetUserDefaultUILanguage`: русский → `ru`, иначе `en`).
- Смена языка применяется сразу: меню трея строится заново, окно перерисовывается.
- Логи — на английском.

## 7. Окно настроек

egui/eframe 0.36 (рендерер glow), ~680×480, вкладки слева:

| Вкладка | Содержимое |
|---|---|
| Устройство | карточка текущей ленты (имя, id, IP, fw, статус); найденные ленты + «Выбрать»; «Искать»; ручной IP + «Подключиться» (проверка IPv4); «Проверить подключение» (результат, время); число LED 1–120 (для Этапа 2) |
| Подсветка | выбор цвета (HSV) + HEX; яркость 1–100; пресеты: клик — применить, «+» — сохранить текущий, ПКМ — удалить; вкл/выкл |
| Общие | язык; «включать ленту при запуске приложения»; действие при выходе |
| Диагностика | версия, IP, состояние подключения и сессии, последние 20 ошибок, «Открыть папку логов», «Скопировать сводку» |

- Изменения применяются сразу; кнопки «Сохранить» нет.
- Окно уже открыто → повторный клик выводит его на передний план
  (`AllowSetForegroundWindow` + поиск окна по PID).
- `--settings` без фонового процесса → сообщение и кнопка «Запустить».
- Шрифты по умолчанию egui должны покрывать кириллицу; проверить при реализации,
  при необходимости встроить шрифт.

## 8. IPC

- Named pipe, имя включает SID пользователя и номер сеанса; DACL — только текущий
  пользователь; `PIPE_REJECT_REMOTE_CLIENTS`. TCP-порты не открываются.
- Протокол «запрос → ответ», одна строка JSON на сообщение (`serde_json`).
  Запросы: `GetState`, `Discover`, `SelectDevice`, `SetManualIp`,
  `TestConnection`, `ApplyStatic`, `SetPower`, `UpdateSettings`, `OpenSettings`.
  Ответ: `Ok`, `Error { message }` или `State(Snapshot)`.
- Долгие операции (поиск, проверка) не блокируют ответ: «принято», результат —
  в последующих снимках состояния (флаг «идёт поиск», список найденных лент).
- Окно опрашивает `GetState` ~4 раза в секунду, пока открыто.
- Сервер синхронный: поток на подключение, запрос-ответ, без overlapped I/O.

## 9. Настройки

Файл `%APPDATA%\ObsidAmbilight\config.toml`, пишет только фоновый процесс.

```toml
version = 1

[device]
id = ""
name = ""
model = "Chameleon2"
last_ip = ""
manual_ip = ""
led_count = 60

[static]
power = "on"
color = "#F5D4A1"
brightness = 40
presets = ["#F5D4A1", "#FFFFFF", "#FFB46B", "#FF0000", "#00FF00", "#0000FF", "#8A2BE2", "#00CED1"]

[startup]
power_on = true

[app]
language = "auto"
exit_action = "keep"

[advanced]
log_level = "info"
```

- Отсутствующие ключи — значения по умолчанию; незнакомые ключи игнорируются.
- Невалидный TOML → исходный файл сохраняется как `config.bad-<время>.toml`,
  запуск с умолчаниями, предупреждение в «Диагностике».
- Невалидное поле → сброс только этого поля, предупреждение в лог.
  Правила: яркость 1–100; цвет `#RRGGBB`; `led_count` 1–120; IP — IPv4 или пусто;
  язык и `exit_action` — из перечня; пресетов ≤ 16, без дубликатов.
- Запись атомарная: временный файл → замена. Запись с задержкой ~0,5 с при серии
  изменений.
- Токен сессии в файл не пишется никогда.

## 10. Ошибки, логи, один экземпляр, выход

- Интерфейс не ждёт сеть: трей и окно только ставят команды в очередь и читают
  снимок. UDP-ответ ≤ 0,6 с, рукопожатие ≤ 3 попытки (≈ 2 с худший случай).
- Ошибки для пользователя: иконка, строка состояния, «Диагностика» (кольцо из 20).
- Логи: `%APPDATA%\ObsidAmbilight\logs\obsid-ambilight.log` и `settings.log`;
  ротация при запуске (> 1 МБ → `.1`, одна копия); собственный писатель на `tracing`;
  уровень из `advanced.log_level`; токены замаскированы.
- Паника: hook пишет в лог. Падение worker → ошибка в трее и перезапуск потока,
  не более 3 раз подряд, затем ожидание действия пользователя.
- Один экземпляр: mutex `Local\ObsidAmbilight.Instance`. Повторный запуск
  отправляет `OpenSettings` по каналу и завершается; канал не отвечает →
  `MessageBox` «уже запущено, но не отвечает».
- Выход: остановить приём команд → `exit_action` (`keep` — ничего не слать,
  `off` — `set_power off`, ожидание ≤ ~1 с) → закрыть процесс настроек → удалить
  иконку. При аварийном завершении выключение не гарантируется.

## 11. Модули

```text
src/main.rs                 диспетчер: фон | --settings
src/app/state.rs            ConnState, Snapshot
src/app/commands.rs         Command, схлопывание
src/app/controller.rs       машина состояний (чистая)
src/app/worker.rs           поток ленты, DeviceLink
src/config.rs               загрузка, проверка, атомарная запись
src/i18n.rs                 Strings RU/EN, выбор языка
src/ipc/mod.rs, pipe.rs     сообщения, named pipe (Win32)
src/platform/               mutex, пути, язык Windows
src/ui/tray.rs, icons.rs    трей Win32, иконки
src/ui/settings/            egui: device, lighting, general, diagnostics
src/diagnostics.rs          логи, ротация, кольцо ошибок
```

`protocol`, `discovery`, `reconnect` и `obsid-poc` остаются; `reconnect::Backoff`
используется контроллером.

**Новые зависимости:** `eframe` 0.36 (окно), `serde` 1 + `toml` 1 (конфигурация,
требование п. 10 ТЗ). Дополнительные функции `windows-sys` (Shell, GDI,
WindowsAndMessaging, Pipes, Security, Threading, Globalization).

## 12. Тестирование

Автоматические (без железа):

- `controller_tests` — первый запуск (одна/несколько/ноль лент), сбой → Offline →
  повторы с растущей паузой → восстановление Static/Off, ручной IP, схлопывание,
  действие при выходе;
- `config_tests` — умолчания, круговое сохранение, сброс плохого поля, битый
  файл → резервная копия, незнакомые ключи, атомарная запись;
- `ipc_tests` — сериализация сообщений, реальный named pipe в одном процессе;
- `i18n_tests` — выбор языка по LANGID;
- существующие `protocol_tests`, `discovery_tests`.

Каждая задача: `cargo fmt --check`, `cargo clippy --all-targets -- -D warnings`,
`cargo test`.

Ручные (раздел Этапа 1 в `docs/testing.md`): автоподключение при запуске; цвет и
яркость из трея и окна; отключение питания ленты → Offline → восстановление;
второй запуск открывает настройки; перезапуск Проводника; оба `exit_action`;
смена языка; Apple Home после каждого сценария; замер RAM/CPU фонового процесса
в Static и процесса настроек.

## 13. Критерии готовности Этапа 1

- Приложение без ручного IP находит ленту, при следующем запуске подключается
  само и применяет статический цвет.
- Цвет, яркость, питание меняются из трея и окна без перезапуска и сохраняются.
- При недоступной ленте интерфейс не зависает, состояние — «Устройство
  недоступно», после восстановления связи Static возвращается сам.
- Второй экземпляр не создаётся.
- Интерфейс полностью доступен на русском и английском.
- Фоновый процесс в Static укладывается в цели п. 12 ТЗ (проверено замером).
- Все автоматические проверки зелёные.

## 14. Риски

- Перемежающиеся отказы Apple Home после LAN-трафика (Этап 0) — причина не
  установлена; смягчение — минимальный трафик; контроль в ручных сценариях.
- Объём exe растёт из-за eframe (оценка — несколько МБ); приемлемо для одного exe.
- `id` в ответе поиска на прошивке 36 — 12 hex-цифр (вероятно, MAC); формат не
  документирован, хранится как строка без интерпретации.
